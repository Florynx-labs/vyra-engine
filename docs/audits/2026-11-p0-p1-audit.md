# VYRA Engine — P0/P1 Audit & Hardening

**Audit branch:** `work/p0-p1-performance-hardening`  
**Baseline:** `main`, v0.1.4  
**Audit date:** 2026-11-24  
**Scope:** repository architecture, profiler, job scheduler, ECS storage, allocator, CMake test configuration and release documentation.

## Executive summary

The repository already contains the v0.1.4 profiler and worker-pool foundations, but the release notes and roadmap overstate their validation. The highest-risk findings were in asynchronous job completion/shutdown and profiler snapshots/memory accounting. This branch hardens those paths, adds a fixed-size object pool, exposes ECS capacity reservation, and expands deterministic tests.

**Important:** this audit was performed against source files available on the default branch. A native compiler/build environment was not available in this session, so no successful build or test execution is claimed. The PR must remain unmerged until CI has run and the maintainer has reviewed the results.

## P0 — Correctness and lifecycle

| Area | Finding | Change |
|---|---|---|
| Job queue | Shutdown could stop workers while queued jobs remained, leaving handles pending forever. | Queue shutdown now drains queued work; scheduler stops accepting new work and waits for outstanding jobs before joining workers. |
| Job completion | Calling `promise.get_future()` from each wait is only valid once. | Jobs now retain a shared future; repeated and concurrent waits observe the same completion state. |
| Job scheduler | `WaitForAll` busy-polled and pending-count access could dereference a null queue. | Completion condition variable + outstanding-job counter; null-safe queue access. |
| Job scheduler | Scheduling could race scheduler shutdown and queue destruction. | Lifecycle mutex serializes initialization, scheduling and teardown; accepting-work state closes before draining. |
| Job execution | Non-standard exceptions could escape a worker thread. | All exceptions mark the job failed, complete its shared state, and are logged without terminating the worker. |
| Profiler | Public getters returned references to mutable state without holding the mutex. | Snapshot-by-value getters now lock while copying. |
| Profiler | `high_resolution_clock` is not guaranteed monotonic. | Timing now uses `steady_clock`. |
| Profiler memory | Free accounting could underflow unsigned current usage. | Free accounting clamps unmatched bytes and emits a warning. |

## P1 — Performance foundation

- Added header-only `vyra::core::ObjectPool<T, BlockSize>`: stable-address blocks, aligned in-place construction, free-list reuse, destruction, capacity/size reporting and mutex protection.
- Added tests for object reuse, destruction, block growth and constructor exceptions.
- Added `Registry::Reserve` and `Registry::Capacity` so scene loading can pre-size EnTT entity storage.
- Expanded job tests for queued-work draining, failure states, repeated waits and reinitialization.
- Expanded profiler tests for snapshots under concurrent reads/writes and invalid free accounting.
- Made GPU integration-test target optional through `VYRA_BUILD_GPU_TESTS`, allowing headless CI to build and run unit tests without a Vulkan runtime.

## Remaining risks / follow-up issues

These are not represented as fixed by this PR:

1. Renderer still reaches into Vulkan handles directly; finish the RHI-only rendering path before adding another graphics backend. See [issue #7](https://github.com/Florynx-labs/vyra-engine/issues/7) and [issue #14](https://github.com/Florynx-labs/vyra-engine/issues/14).
2. ECS `Entity` still stores a non-owning raw `Registry*`; lifetime-safe entity ownership/handles need a separate API design. See [issue #13](https://github.com/Florynx-labs/vyra-engine/issues/13).
3. RHI resource handles still need generation validation, use-after-free diagnostics and a clear shared-ownership policy. See [issues #4–#6](https://github.com/Florynx-labs/vyra-engine/issues/4).
4. GPU profiling is still a placeholder; Vulkan timestamp queries and frame-latency calibration are not implemented.
5. Job priorities are represented in the API but the queue remains FIFO. Dependencies, cancellation and work stealing are future work.
6. The asset registry is a foundation, not a complete import/decode/cache pipeline.
7. Cross-platform compilation and Vulkan validation still require CI runners and real hardware/driver coverage.

## Validation plan

Run from a clean checkout:

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DVYRA_BUILD_SAMPLES=OFF \
  -DVYRA_BUILD_GPU_TESTS=OFF
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Then run a separate GPU-enabled build on a machine with a supported Vulkan SDK/driver and enable validation layers. CI results, compiler versions and platform coverage must be recorded before merging.
